Brief: `docs/iteration3/P6-standins.md`. Agreed with the user on 2026-11-09 ("carry on with the suggested items and the lean implementations"). Serves FB-c, CR1, CR3 (DR-8), CR4, G3, SR4, U1. Hand-off briefs read: W0 (C1, C5–C8, C10, the contracts P6 consumes); P2's `reach/001` D9 (the `standins` key in `TP_FAMILIES`).

| # | Decision | The brief said | Agreed | Why |
|---|---|---|---|---|
| D1 | OpenAI-compatible stand-in | Open question; recommend later | **Later.** The ledger lists AI and S3 dependencies as not tested, with the reason | Two kinds (HTTP, SMTP) already show the extension point (U2, DR-12) |
| D2 | Where `checks.value.dependencies` survives | C5: P6's discovery writes it | `dependencies.run` sets `d.dependencies`. **Request R1:** `step_resolver` writes it to `checks.value.dependencies`, and the wired entries to `checks.value.families.dependencies` | `step_resolver` runs after the hook and replaces `values["checks"]`, so C5 couldn't hold as built. Through `families` it reaches `$TP_FAMILIES` with no change to `families_config` (P2) |
| D3 | What the families call | Not stated; C5 has no trigger | **Contract addition (user OK 2026-11-09):** a dependency entry gains optional `trigger: "METHOD path"` and `setup: {op, body} \| null`. A stand-in entry gains optional `command: [..]`. W0's brief is updated | Case ids are `G:<family>:<METHOD> <path>`, like today's families, so the op must be stored. The HTTP fake runs from the runner image with `python -m platform_rt.standin`, and Mailpit needs `--enable-chaos`: P2 needs the command |
| D4 | Verifying a wiring | "A triggered action leaves a line in the journal" | Discovery restarts the stack with the stand-ins, then calls each POST op once (capped in `config/dependencies.yaml`) and compares the journals before and after. The first op that leaves a line is the `trigger`, with the probe id as `evidence`. No line: `unwired`, with the reason, and a `setup` question | Running decides (CR1, DR-1); no model picks the trigger |
| D5 | The model's part | "When a name isn't in the code, the model proposes it" | One call (Haiku, K4), only when the code shows a dependency signal (from the yaml) but no convention name matched. Its proposal is verified like any other. Wave 1 uses a scripted fake (K5). The prompt is `tp/stages/discover/prompts/wiring.md` | Discovery's one-call-per-step rule (D1 of discover/001) |
| D6 | Stand-in layout | Not stated | One HTTP fake `tp-standin-http` for every HTTP dependency, each env var pointing at its own path (`/notify_url`), so journal lines are attributed by path. One Mailpit `tp-standin-mail` | One process per kind (K3) |
| D7 | `dependency_called` | The run-prefixed value we wrote reaches the stand-in | Every string we send through the trigger is run-prefixed (`record.name()`; `format: email` gets `@example.test`). Every one must appear in what the stand-in received (HTTP: the request on its path; SMTP: the message's `To`/`Cc`/`Bcc` and subject) | Drops-body and wrong-recipient each lose the value |
| D8 | `dependency_failure_handled` | Sync: in time, not 500; async: completes and stays readable | One fault per test (C1 has one mode). HTTP: `delay_s: 8`; the trigger must answer within 4 s, not with a 5xx other than 502–504, and a 2xx create must read back. SMTP: Mailpit's chaos, `Recipient` 451. The fault is cleared in `finally`, and the record carries `fault` | One check covers sync and async without classifying them. Chaos was **verified by running** Mailpit locally (v1.33.0 on disk; the pin is v1.33.1): `PUT /api/v1/chaos {"Recipient": {"ErrorCode": 451, "Probability": 100}}` refuses at RCPT, `{}` clears it, and it needs `--enable-chaos`. So the "stop the stand-in" fallback isn't needed |
| D9 | `dependencies.json` | One per run, redacted | Each dependency test keeps what the stand-in received in `observed.received` (redacted with the record). `platform_rt.dependency.ledger(results)` builds the file. **Request R2:** execute adds `dependencies.json` to the run's files | Execute writes the run's files, and `record.write` already redacts them |
| D10 | Webhooks registered through the API (`via: spec`) | Discovery looks at spec fields named url, webhook or callback | Built now: `setup` registers the stand-in URL, then the trigger runs as in D4. Unit-tested against a synthetic spec. The fixture isn't extended | c1 (Memos) needs this path. The family is what must bite (DR-8), and the fixture's env path proves it |
| D11 | Tests | Fixtures only | The default suite runs the fixture's `app.py` (each seed patched into a tmp copy) and the HTTP fake as local processes. SMTP runs in `docker`-marked tests with Mailpit, compose project or container prefix `it3-p6-` | Fast and CI-safe; Docker only where Mailpit is needed |
