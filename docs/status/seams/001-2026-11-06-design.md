# Seams (iteration 2, stage A) — design

Stage document: `docs/iteration2/A-seams.md`. Debate held 2026-11-06. The stage split itself (A–G) and review decisions R1–R10 are recorded in the master, `docs/tiktokoa-iteration2-dev-plan.md` §8.

| # | Item | Stage document said | Agreed | Why |
|---|---|---|---|---|
| D1 | Where template-only inputs live | Open question (`sut/` or `targets/<slug>/`) | A new `targets/<slug>/` folder holds every hand-written input for a target. The template moves there as `targets/fastapi-template/`: `profile.yaml` (D2), `requirements.md` and `patches/` from `sut/`, `factories.py` from `tp/stages/env/factories.py`, `seeded.yaml` from `tp/stages/gate/seeded.yaml`. Discovered profiles (stage D) are run artifacts cached per commit under `data/`, not files in `targets/`. | `factories.py` and `seeded.yaml` are template data inside `tp/`; the allow-list can't reach zero while they're there. The folder layout itself shows "targets are data". |
| D2 | `sut.yaml` | An adapter `sut.yaml` → profile | **One-shot conversion** to a checked-in `targets/fastapi-template/profile.yaml` in the `TargetProfile` schema (template-only settings become strategy parameters; fields carry `source: override`). The profile is the single source of truth. A **reverse shim** builds the legacy config dict from the profile, so call sites not yet moved keep working; it is deleted when the allow-list reaches zero. The M8 branch-target overlay (`target.json`) lays over the profile instead of over `sut.yaml`. | A permanent adapter means two formats to keep in sync. The reverse shim keeps the strangler-fig property (green after every step) with one format. |
| D3 | `sut.yaml` field mapping | — | `compose`, `lifecycle.migrate`, `health`, `testinfo` → `reach` (`container`). `lifecycle.db_probe`, `migrations` → `state` (`transaction`). `patches`, `flags`, `code_scope` → `mutation` (`in_process`). `surfaces.api` → `spec` (`served`). `auth` → `auth` / `creds` (`override`). `name`, `repo`, `ref`, `type`, `env` → top-level target fields. | Each setting belongs to the strategy that uses it. |
| D4 | Allow-list test: scope | "No target literals under `tp/`" | Everything under `tp/` that git tracks (`.py`, prompts, YAML, templates), **excluding** `tests/`, `fixtures/` and `expected/` directories, which use the template as sample data on purpose. | Platform code must be target-free; platform tests need a sample target. |
| D5 | Allow-list test: patterns | Literal list (`backend/`, `/api/v1`, alembic, `FIRST_SUPERUSER`, `item`) | A regex list in the test: `backend/`, `/api/v1`, `/app/backend`, `alembic`, `FIRST_SUPERUSER`, `mailpit`, `BUG_[A-Z]`, `/items`, `full-stack-fastapi`, plus target names `paperless`, `memos`. `item` alone is too generic, so `/items` is used. | Precise patterns keep false positives near zero. |
| D6 | Allow-list test: mechanism | "May only shrink" | A ratchet: the test stores a `{file: count}` baseline. It fails if a file's count goes up, if a new file appears, or if a count went down without the baseline being lowered to match. | Keeps the baseline honest in both directions. |
| D7 | Allow-list starting count | ~15 files | Measured 2026-11-06 at `7b1d942`: **43 lines in 17 files** (largest: `env/service.py` 7, `report/export.py` 5, `gate/seeded.yaml` 4, `core/sut.py` 4). | Measured, not estimated. |
| D8 | Framework coupling | — | The literal test does not catch framework coupling (e.g. `spec/code_index.py` is FastAPI-only). That stays tracked by hand in A's coupling table. | A text match can't see semantics; say so rather than over-claim. |
| D9 | Config location | `config/priority.yaml` | Repo-root `config/`, holding `priority.yaml` now and `discovery.yaml` in stage D. Outside `tp/`. | Configuration is data; it doesn't count against the allow-list. |
| D10 | Verification during A | r-0002 replay unchanged | `uv run pytest` after every step. One manual r-0002 replay (Docker + real model calls) at the end of A, wrapped in `caffeinate -i`. | Call-site moves are ~80 edits across seven stages; the replay is slow and costs money, so once is enough. |

## Build steps (numbered for status files)

- **A1** Characterise: allow-list ratchet test (D4–D7) and `rank()` regression test with default weights.
- **A2** Priority module + `config/priority.yaml` (case weights); `rank()` reads it; the regression test still passes.
- **A3** `TargetProfile` / `StrategySet` / interfaces / resolver; `ctx.profile` and `ctx.strategies`.
- **A4** Move the template into `targets/fastapi-template/` and convert `sut.yaml` → `profile.yaml`; reverse shim; branch-target overlay on the profile.
- **A5** Move call sites stage by stage (gate, generate, env, execute, triage, spec, report, baseline), literals into profile fields; lower the ratchet baseline as each lands.
- **A6** Held-out repo list written down (master §9). r-0002 replay.
