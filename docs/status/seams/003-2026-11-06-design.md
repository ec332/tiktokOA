# Seams (iteration 2, stage A) — design addendum: the template's role

Adds to `seams/001` (D1 put the template's inputs in `targets/fastapi-template/`). Settled with the user on 2026-11-06.

## D11 — The template is a calibration target, not the platform's default

**Question raised:** "can you drop this specific one in favour of a generic workflow, the idea is to prove the generalisability of this pipeline".

**Options weighed:**
- Drop the template entirely. This loses the only ground truth: 4 planted bugs, the mutation gate, and r-0002's 6 known defects. Without known answers, a reported defect on an unseen repo can't be told from a false positive (grading criterion "credible test results").
- **Keep it, demoted to a calibration target (agreed).**

**Agreed:**
1. Generalisability is shown by the same pipeline running on repos that have **no hand-written files**: B (a profile only), D (a discovered profile), and the held-out Gitea and Mealie (master §9).
2. The template takes the same discover → profile → run path as any other repo once D lands. Its folder shrinks to the **optional per-repo extras** that can't be discovered: the planted-bug patches (`flags`, `testinfo`, `trace`, `fix-pagination`), `seeded.yaml`, and the in-process harness and factories its mutation gate needs.
3. Its hand-written `profile.yaml` becomes a D acceptance check. Discovery on the template's repo URL must reproduce every field the extras don't need. Each field that differs is either a discovery bug or a documented override.
4. On the UI and in the write-up, the template is one target among several, labelled "known answers (calibration)", not "the" target.

**Not changed now:** the folder name and layout stay as built in `seams/002` until D settles the naming rule (`owner__repo` from the URL is the leading option) and the override layering. There is no code change in stage A.

**Plan documents updated:** master §4 (the template row's role) and §8 (R11); `D-discover.md` "Done when".
