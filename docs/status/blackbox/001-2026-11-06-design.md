## Decisions

### D1. `namespace` cleanup — once per run, ledger-based
- **Stage doc said:** "run-prefixed resources plus cleanup"; open question per test vs per run.
- **Agreed:**
  - Names are unique **per test execution**: `tp-<run>-<nonce>-<label>`, produced by `platform_rt` (`ns.name("label")`). A per-run prefix alone would collide under the gate's K=5 + shuffle on unique-name constraints.
  - Every 2xx create made through `platform_rt`'s HTTP client is appended to a ledger (method, path, id/Location). Read-only and failed calls are not recorded.
  - At end of run, `State` deletes the ledger in reverse order, best effort, without stopping on errors. Leftovers go to a `cleanup.json` artifact (`deleted`, `failed`, `unknown_delete_route`). Leftovers never fail the run.
  - For `container` reach, teardown is the real cleanup. The ledger delete still runs so E inherits a tested path.
  - `State.reset()` starts a new nonce scope; it does no I/O.
  - A start-of-run sweep of old `tp-` prefixes is only needed for external targets → stage E.
- **Why:** per-test delete needs an inverse for every generated call and adds latency to every gate repetition, for isolation that unique names already give.

### D2. List assertions filter to the test's own namespace
- **Stage doc said:** nothing.
- **Agreed:** the generate binding prompt gets one rule: assertions over a collection count or match only items carrying the test's own prefix. It rides on the prompt edit B already makes (removing the template's example path). The generate version hash and LLM cache change, which is expected.
- **Why:** on a shared, non-reset database, "list returns N" depends on what other tests created.

### D3. Compose — parse and rewrite into the run directory
- **Stage doc said:** open question, as-is vs rewritten.
- **Agreed:** the platform loads the repo's compose file and writes `<run>/compose.yml`, kept as an artifact, with these generic rules:
  - Keep: `image`, `build`, `command`, `entrypoint`, `environment`, `depends_on`, `healthcheck`. `env_file` is resolved and inlined.
  - Drop: `ports`, `restart`, `container_name`, `network_mode`, `privileged`, `cap_add`, `devices`, `pid`, `ipc`.
  - Host bind mounts → subfolders of the run's temp directory. Named volumes → fresh volumes scoped to the compose project `tp-<run>`, removed at teardown.
  - Add: the run network (D5), `cpus`/`mem_limit` per service from `config/sandbox.yaml`, label `tp.run=<run>`.
  - The profile's environment entries (e.g. admin credentials, with secrets as references to the secret store) are merged into the app service.
  - The profile names the app service and its port (`reach.value.service`, `reach.value.port`). There are no rules about specific targets.
- **Why:** a compose override can't cleanly remove `ports`, and a written file is auditable. An unknown key that could touch the host makes the rewrite fail closed.

### D4. Image at the commit under test — tag-matched image first, build second
- **Stage doc said:** "build from the repo's compose/Dockerfile".
- **Agreed:**
  - `container` reach checks out the repo at a ref. If the profile gives `reach.value.image_tag_from: ref`, image references whose tag is `latest` are rewritten to the checked-out tag (`paperless-ngx:latest` → `:v3.4.2`). The run fails if that tag can't be pulled. `commit_tested` = the tag's commit.
  - Services with `build:` are built at that commit. Images are cached per commit (`tp-<slug>:<sha12>`).
  - In B the build path is contract-tested **against a fake only** (a tiny Dockerfile). Its first real target is Memos in D.
- **Why:** the Paperless compose uses a prebuilt image. Building Paperless from source (Angular frontend + OCR tools) costs a lot of time and disk and proves nothing more. This matches the master's risk row ("an image is used only when its tag matches").

### D5. Network — runtime has no internet; builds have the default network; no domain allow-list
- **Stage doc said:** outbound limited to what the build needs; open question on runtime internet.
- **Agreed:**
  - Run network `tp-<run>` is `internal: true`. Target services and the black-box runner join it; the runner reaches the app by service DNS name (`http://webserver:8000`).
  - On Docker Desktop, an internal network can't publish ports. Host-side calls (health, spec fetch, auth probing, ledger cleanup) go through a `socat` forwarder sidecar that sits on both the run network and the default bridge. It publishes `127.0.0.1:<random>` → `<service>:<port>`, inbound only. `Reach` exposes that as the platform's base URL.
  - `docker build` and image pulls use Docker's default network: unrestricted outbound, **stated plainly** in the report's environment section.
  - A per-domain build allow-list (PyPI / npm / Go proxy) needs an egress proxy → **parked** (not in iteration 2).
- **Why:** an internal network is one line and is enforced by Docker; a domain allow-list is a separate component with no demo value inside 0.5 day.

### D6. The resolver stays a lookup; inference rules move to D
- **Stage doc said:** B implements a resolver rules table ("external if live URL else container", "transaction if the harness can import…", …).
- **Agreed:** A's `resolve()` already maps `value.strategy` → implementation, and stays that way. The rules table becomes the **profile-writing rules of stage D** (discovery decides each field's strategy, with evidence). B's hand-written profile names every strategy directly.
- **Why:** two places choosing strategies would contradict "the same profile always gives the same strategies"; inference is discovery's job.

### D7. Scope moved from B to D
- **Stage doc said:** B builds auth `bearer_login`, spec `repo_file` and the `Reach.exec` allow-list.
- **Agreed:** all three move to D, whose target (Memos) is their first real case:
  - Paperless's token is `Authorization: Token <t>` (fetched from `POST /api/token/`), which is `token_header` with a login step, not `bearer_login`.
  - Paperless serves its spec; `repo_file` would only have a fake to test against.
  - Paperless creates its admin from environment variables; AI-proposed commands only appear in D.
- **B keeps:** reach `container` (image + build path), spec `served`, auth `basic` and `token_header` (with an optional login step: `login: {path, body, token_field, scheme}`), data `spec_derived`, state `namespace`, the sandbox (network, limits, no host mounts) and redaction.
- **Why:** each strategy gets a contract test against a fake **and** a real target; for these three the real target is Memos.

### D8. Read-back retry budget comes from the profile; B exercises it on a document upload
- **Stage doc said:** retry for up to 5 s.
- **Agreed:**
  - `platform_rt.eventually(fn, timeout=…)` retries with exponential backoff (0.1 s → 1 s cap). The timeout comes from `data.value.read_back_timeout_s` (default 5).
  - The Paperless profile sets it to 60, with evidence "async consumption via Celery; OCR of a one-page PDF". The value is measured on the first real run and corrected there.
  - Every pass records `attempts` and `waited_s`. The gate classifies a test that passes in all K runs with retries as `eventually_consistent`, not flaky.
  - B's requirement text includes one upload → task (`/api/tasks/?task_id=`) → document read-back flow, so the retry really runs, plus synchronous CRUD on tags and correspondents.
- **Why:** an upload returns a task UUID, not a document ID, and OCR routinely exceeds 5 s. A fixed 5 s would make the one case R4 moved here for always fail.

### D9. Redaction covers encoded forms; secrets never reach the test folder
- **Stage doc said:** redact headers and known secret values; a redaction test scans artifacts.
- **Agreed:**
  - Secret variants scanned and redacted: raw value, `base64(user:pass)` for basic auth, URL-encoded, and JSON-escaped.
  - Redacted headers: `Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, and any header whose name contains `token`, `key` or `secret`.
  - Secrets reach the runner container only as environment variables (`TP_SECRET_*`). Generated tests read them through `platform_rt`, never as literals, and the test folder is scanned before it is sealed as an artifact.
  - The redaction test runs over **every** file in the run directory (including `compose.yml`, logs and `cleanup.json`) and fails on any variant.
- **Why:** a basic-auth header holds the base64 of the password, so a raw-value scan would pass while the secret leaks.

### D10. The hand-written profile lives under `tests/`, selected by `--profile`
- **Stage doc said:** "kept as a test fixture (not under `tp/`)".
- **Agreed:** `tests/fixtures/profiles/paperless-ngx/{profile.yaml, requirements.md}`. `tp run --profile <path>` (and `TP_PROFILE`) selects a profile file directly. There is no `targets/paperless-ngx/` folder. D's acceptance compares its discovered profile to this fixture field by field.
- **Why:** keeps the "no hand-written files for new targets" claim true; the fixture is test input, not platform input.

### D11. Kept from the stage document as written
- The gate runs stability (K=5 + shuffle), skips planted bugs, and records `strength: not_measured`.
- A contract test per strategy, against a fake and Paperless.
- The template is unchanged: `uv run pytest` green including Docker tests, and the old-vs-new comparison as in `seams/004`.
- Literals removed by B: the Alembic head check in `tp/core/sut.py` and the example path in `generate/prompts/binding.md`.

## Fake target for contract tests
One small in-repo HTTP app (`tests/fakes/blackbox_app/`, starlette, run as a container on the run network) implementing: basic and token auth (with a login route), a served OpenAPI spec, CRUD with unique names, and one resource that appears only after a delay (to test `eventually`). One Dockerfile, which is also the fake for the build path (D4).

## Build order (scope items, numbered for status files)
1. `platform_rt`: namespace names, the create ledger, `eventually`, and secrets from the environment.
2. `images/runner-blackbox` (python + platform_rt + httpx + schemathesis).
3. Compose rewrite + sandbox config + run network + forwarder (D3, D5).
4. Reach `container`: image tag matching + build with a per-commit cache (D4).
5. Spec `served`; auth `basic` and `token_header` (+ login); data `spec_derived`; state `namespace` (D1).
6. Generate: HTTP-only tests for the black-box runner; the binding prompt rule (D2); literal removals.
7. Gate: `strength: not_measured`, `eventually_consistent` (D8).
8. Redaction in sealing + the redaction test (D9).
9. `--profile` / `TP_PROFILE`; the Paperless fixture profile + requirements (D10).
10. The fake app + a contract test per strategy; the Paperless end-to-end run; the template's old-vs-new check.
