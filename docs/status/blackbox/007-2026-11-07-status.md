## 6. Working rules (from CLAUDE.md and the user's preferences)

- **One stage at a time**, in dependency order. **Before each stage, a design debate:** challenge the stage document, recommend; don't just list options. **No code until the user says go.** Then write a `design` file before coding.
- **Status files** `docs/status/<stage>/NNN-YYYY-MM-DD-<design|status>.md` are **append-only**: never edit one; write a new one that names what it corrects. Folders: `seams` (A), `blackbox` (B), `checks` (C), `discover` (D), `external` (E), `autonomy` (F), `demo` (G). Add them with `git add -f`. Plan documents *are* edited to match decisions; keep the master tracker's Status column current. Never edit `docs/iteration2/original-dev-plan-snapshot.md`.
- **Context scope:** read the master plus the current stage's document only, and the source files the stage changes. If you need another stage's document, read only the part you need and tell the user which part and why.
- **Commits:** only when the user asks. Use owner tags from `docs/folders.yaml` (`[gate] C3: …`). Cross-cutting work is split per owner, and `tp check-folders --commits <range>` must pass.
- **Cost:** the smallest model that passes, measured (Haiku 5.5 by default). No golden replays of real LLM output in tests: use scripted fakes plus documented real runs. One sample by default. Wrap Docker and long runs in `caffeinate -i`.
- **Lean POC scope:** build only what the current stage needs; park the rest.
- `uv run pytest` stays green after every step. A new piece of target-specific behaviour goes in the profile or a strategy, never behind a target name in `tp/` (the ratchet test enforces it).
