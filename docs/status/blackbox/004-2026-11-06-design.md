# Black-box path — design: pipeline integration (stage B, iteration 2)

Adds to `001` + `002`; written after build checkpoint `003`. The user said "go" after `003` reported that spec, cases and the generate checker are tied to the template. These are the decisions taken for that gap. Each keeps the template's behaviour (and its rendered prompts) byte for byte.

## D14. Spec without source: an index built from the OpenAPI document
- **Gap:** the spec stage indexes FastAPI source (AST) and wants `file:line` evidence. A black-box target has no source.
- **Decided:** when the profile has no `spec.value.source_dir`, the spec stage builds its index from `ctx.strategies.spec.openapi()`:
  - One pseudo-file per operation, `openapi/<path>/<METHOD>.yaml`, holding that operation as YAML.
  - Plus `openapi/components.yaml`, holding the schemas the kept operations reference.
  - Focused to the run's `routes` option (all operations if none is given).
  - Evidence cites `openapi/…:line` as it cites source today, and the same checks validate it.
- **Why:** same stage, same prompts, same evidence rule. It needs no new prompt and costs only the focused excerpt.

## D15. Factories and the `make` description come from the data strategy
- **Gap:** cases' precondition names, the scaffold `REGISTRY`, the static checker and the binding prompt's `make` paragraph are the template's factories.
- **Decided:**
  - Data strategies expose `factories()` (precondition names) and `doc()` (the `make` paragraph for the binding prompt).
  - `override_module` reads both from the profile (`data.value.factories`, `data.value.doc`; the template's text moves there verbatim, example path included).
  - `spec_derived` gives `["admin"]` and a generic paragraph: `make.admin()`, `make.name(label)` (use it for every name you create; count only your own items), and `eventually(fn, until)` for read-backs.
  - Cases, scaffold and checker take the names as an argument; the constants remain only as defaults for unit tests.
  - `binding.md` gets a `{{MAKE}}` placeholder, so the template's rendered prompt stays identical (its LLM cache stays valid). The prompt file loses its last target literal.
- **Why:** the factories are target data. A second copy of them in code was the coupling.

## D16. Gate without mutation: stability only, `strength: not_measured`
- **Decided:** when `mutation.available()` is false, the gate:
  - runs K + shuffle stability as today;
  - skips handler mutants, seeded bugs and the mutmut matrix;
  - admits stable passes as `ADMITTED_UNMEASURED` (an existing status);
  - reports `strength: "not_measured"` in the verdict and per criterion.
- A node that passes in every run, but needed `eventually` retries in any, gets `eventually_consistent: true` (D8).

## D17. `sut.load()` overlays the web-chosen branch only for in-process targets
- **Gap:** `data/sut/target.json` (the template branch picked in the UI) was laid over *any* active profile, so a Paperless run would have read the template clone's repo and ref. `profile.legacy()` also assumed the template's compose dict.
- **Decided:** the overlay applies only when `mutation.strategy == "in_process"`, since branch targets exist to mutate changed lines. `legacy()` passes a non-dict `compose` through as `{}`.

## D18. The runner reads the spec from the profile's path
- `platform_rt`'s `api.openapi()` uses `$TP_OPENAPI_PATH` when set, so the runner and the host read the same document. The black-box runner sets it from `spec.value.openapi`.
- The Paperless profile asks for `?format=json`, since drf-spectacular serves YAML by default. Its `base` becomes `/api`, so cases group flows by resource (`tags`, `documents`, …) with the existing first-segment rule.
