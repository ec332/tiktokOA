## D12. No fake target app — test each strategy against what its logic depends on (replaces "Fake target for contract tests")
- **`001` said:** one in-repo starlette app (`tests/fakes/blackbox_app/`), run as a container, serving as the fake for every contract test and the build path.
- **Agreed:**

  | Strategy | Depends on | Contract test |
  |---|---|---|
  | Auth `basic`, `token_header` (+ login); spec `served`; data `spec_derived`; state `namespace` (ledger, cleanup, leftovers); `platform_rt.eventually` | HTTP request/response | `httpx.MockTransport` handlers scripted inside each test (401, login without token field, 404 ×N then 200, failed DELETE → `cleanup.json`, duplicate-name create). Default suite, no Docker. |
  | Reach `container`: compose rewrite + tag matching | YAML → YAML | Pure-function test on a copy of Paperless's real `docker-compose.sqlite.yml` and `docker-compose.env` kept as fixtures: ports dropped, bind mounts moved, volumes scoped, `:latest` → ref tag, unknown host-touching key → error. Default suite. |
  | Reach `container`: run network, forwarder, limits, build + per-commit cache | Docker | One `docker`-marked test on a 3-line compose fixture (`build:` from `FROM python:3.12-slim` + `python -m http.server`): forwarder reaches it, no outbound from the run network, a second build hits the cache. A fixture, not a target: no profile, auth or API. |
  | All of the above, for real | Paperless | The end-to-end run (`docker`-marked). |

- **Why:**
  - A fake app is a second target to build, ship as an image and maintain. It pulls Docker into tests whose logic is pure HTTP, and goes against the "scripted fakes, not fake systems" rule.
  - Scripted transports trigger every failure path on demand, in milliseconds, so the default suite covers more and the slow Docker suite stays small.

## D13. `TP_TARGET` accepts a path; the Paperless profile is a target folder under `tests/fixtures/` (replaces D10)
- **`001` said:** `tests/fixtures/profiles/paperless-ngx/` selected by a new `tp run --profile <path>` / `TP_PROFILE`.
- **Agreed:**
  - `TP_TARGET` holding a `/` is taken as a path to a target folder: `target_dir()` returns it as is (~3 lines in `tp/core/profile.py`). A plain slug still means `targets/<slug>/`; unset still means "the only folder under `targets/`" (the template).
  - The fixture is `tests/fixtures/targets/paperless-ngx/{profile.yaml, requirements.md}`, the same layout as `targets/fastapi-template/`.
  - There's no `--profile` flag, no `TP_PROFILE`, and no `targets/paperless-ngx/`.
  - D's acceptance compares its discovered Paperless profile with this fixture field by field. D's discovered profiles (written under `data/`) can be selected through the same path rule.
- **Why:**
  - Putting Paperless under `targets/` would break the default, since two folders means no "only folder": every template command and test would need `TP_TARGET`.
  - A separate `--profile` flag would be a second selection mechanism.
  - Widening the existing one keeps a single mechanism, keeps the template the default, and keeps `targets/` free of hand-written files for new targets.
