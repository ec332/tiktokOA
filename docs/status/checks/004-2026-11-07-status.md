### Fix 1 (the examples go on after spec drift): confirmed, and it found a real defect

**P0 `G:properties:GET /api/tags/`, a real product defect in Paperless-ngx v3.4.2.**

- **Symptom:** Schemathesis sent `GET /api/tags/` with generated filters, and the server answered **500** with Django's HTML "Server Error (500)" page. r-0015 could not have seen this, because each property case stopped at its first undocumented status.
- **Isolated by hand on the same stack** (admin token, one parameter at a time):

  | Request | Status |
  |---|---|
  | `id__in=-1948399055150275721428992` | 500 |
  | `id__in=9223372036854775808` (2^63) | 500 |
  | `id__in=9223372036854775807` (2^63−1) | 200 |
  | `id=-1948399055150275721428992` | 200 |
  | `ordering`, `name__icontains` (non-ASCII), `page_size=-102` | 200 |
  | `page=627863` | 404 |

- **Server log:** `OverflowError: Python int too large to convert to SQLite INTEGER` (`django.request`, Internal Server Error: /api/tags/).
- **Cause:** the `id__in` filter passes integers outside 64 bits to SQLite unvalidated. The `id` filter on the same view rejects them. That is input the server should refuse with 4xx.
- **Stable:** gate `CANDIDATE_DEFECT` on all K=5 runs plus the shuffled run (the properties are derandomized); execute `CONSISTENT_FAIL` 3/3; triage `PRODUCT_DEFECT`.
- **Not localised:** triage has no source for a black-box target (by design, `blackbox/005`). Per the master plan this becomes an issue draft in F, not a PR.
