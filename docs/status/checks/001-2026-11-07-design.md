# Generic checks + triage — design (stage C)

Design debate of 2026-11-07. Inputs: `docs/iteration2/C-checks.md`, the master plan, and the gaps stage B handed on (`blackbox/007` §2, `006` "State of the rest"). The user accepted every recommendation below. `C-checks.md` and the master were updated to match this file.

## Decisions

| # | Topic | What the stage document said | Agreed | Why |
|---|---|---|---|---|
| D1 | Who writes the family tests | Unstated | **Fixed platform code, with no LLM.** One module in `platform_rt`, parametrised by the profile (ID style, paging style) and the verified operations. Family tests skip cases and generate and enter at the gate (stability only). | Zero model cost. The same code runs on every target by construction, which is the done criterion. Drafted feature cases keep today's LLM path. |
| D2 | Schemathesis: library or CLI (open question 1) | Open | **Library, through the pytest integration.** The platform writes a module using `schema.parametrize()`. Each case calls `case.call(session=<platform_rt session>)`. Settings: `derandomize=True`, a small `max_examples` (default 10 per operation) and a recorded seed. Checks: `not_a_server_error`, `response_schema_conformance`, `status_code_conformance`. | Property checks become ordinary tests, so gate, execute (sealed records and redaction), triage and report handle them unchanged. Every request goes through one transport, so auth, the create ledger and per-test cleanup, the 5 req/s budget and **E's safe mode** all live in `platform_rt` (this settles E's routing). Failures come out as curl reproductions (master §3(a)). Derandomizing stops the gate's shuffled reruns from seeing them as FLAKY. |
| D3 | Paging bounds when the spec lists only 200 (open question 2) | "documented status, never 5xx" | **No status oracle.** A 5xx is a product defect. A 2xx must be a well-formed page holding no more than the maximum number of items. Any 4xx is accepted. An undeclared 4xx is reported once, by `status_code_conformance` (as `SPEC_MISMATCH`), not again by the family. | The spec doesn't say which 4xx (or an empty 200) is right, so asserting one would invent a requirement. |
| D4 | What every family asserts | Per-family checks | **Only claims that need no requirement:** never 5xx, never 2xx without credentials (subject to D5), never 2xx for an unknown ID, never 2xx after a delete, declared fields round-trip. Status-code precision (404 vs 400 vs 422) goes to `SPEC_MISMATCH`. | It keeps every product-defect claim from a generic family defensible without a requirement. |
| D5 | Auth required: false positives | "no or invalid credentials → 401/403, never 2xx/5xx" | **An anonymous 2xx is a product defect only on an operation the spec marks as secured.** If the spec says nothing about security (Memos), it is `SPEC_MISMATCH`, and later a Clarify question. A 5xx is always a product defect. | Some operations are public on purpose (the schema, health checks, Memos's public memos). Discovery (D) is what establishes which operations need auth. |
| D6 | `SPEC_MISMATCH` in the report (open question 3) | Open | **Grouped by operation and check**, not by generated example. Each group shows one minimal curl, the spec excerpt (declared statuses or the schema path), what was observed, and an example count. They go in their own section, "Server and spec disagree (N operations)", below P0, never counted as defects, capped (default 10 groups) with the overflow counted. | Raw Hypothesis output is many near-duplicates. Grouping makes it a short list someone can act on. |
| D7 | Assumed criteria failing (B's gap 2: 202 expected, 200 got; 422 expected, 400 got) | Implied to be `SPEC_MISMATCH` | **A fixed triage rule.** When a `SPEC_GAP` criterion fails, look up the observed status in the OpenAPI document for that operation. If the spec declares it, the drafter's guess was wrong: it becomes an information line ("the spec and the server both say 200"), not a finding. If the spec doesn't declare it, it is `SPEC_MISMATCH`. Not done: showing the declared statuses in the cases prompt. | The spec and the server agree; only the drafter's guess was wrong. Deterministic, no LLM. Changing the prompt would touch the cases stage for little gain. |
| D8 | `EXTERNAL_ENV` | A new class: timeouts, 429, 502–504, probe failure | **Merged into the existing `ENV` class.** New rules: a 429 or 502–504 response → `ENV`. A timeout → `ENV` only if the health probe after the batch also failed or was slow; otherwise it stays `INSUFFICIENT_EVIDENCE` (today's rule). The rule text says which case applied. | Triage treats both the same way: the environment is broken, so it isn't a defect. One class fewer for D, E and F to handle. The timeout condition keeps the template's triage unchanged. |
| D9 | `NEEDS_DEPENDENCY` | A new class | **Deferred to D.** In C a hand-written `exclude: [{op, reason}]` list in the profile does the job: families skip those operations, and the report counts them by reason. Async creates (a 2xx POST with no ID, which B records as `untracked`) are excluded from read-back and delete-final automatically, with the reason `async_create`. | Nothing marks an operation as needing a dependency until discovery exists. |
| D10 | Memos done item | "runs on a Memos fixture profile" | **Proved by a contract test** against a scripted HTTP fake with resource-name IDs (`memos/{memo}`) and `pageToken` paging, driven by a hand-written Memos fixture profile. Live Memos runs in D. | The Memos image build is slow and belongs to D. The claim is "same code, different conventions", and a fake proves that. |
| D11 | Choosing which resources to sample ("chosen by priority") | Undefined | **A fixed order:** resources with full create/read/delete first, then spec order, up to 5 per family. The choice is recorded in the artifact. | Priority scores belong to F. |
| D12 | Ceilings | A table by what ran | **Computed from the `StrategySet` plus one fact: whether the property checks ran.** `mutation: in_process` with seeded defects → "Likely defect, catches planted bugs". `mutation: none`, `reach: container`, properties ran → "Stable, property-checked". If the properties didn't run → "Stable". External → defined in E. | A run that skipped the properties mustn't claim "property-checked". |
| D13 | The unbound-case wording (B's gap 1, `report/build.py:70`) | Not in the stage document | **Print the real reason** from `bound_tests[].reason`. | The old line was template advice printed for every target. |
| D14 | Report golden regeneration | Once; the reviewed diff only adds fields | **Once; the reviewed diff adds fields, plus the one wording change from D13.** The master's done item 1 is amended to match. | Bending the rule beats keeping wrong advice in the report. The exception is named, so the review can check it. |
| D15 | Build order | Families listed; cut order separate | **The build order is the cut order:** properties → auth required, unknown ID, invalid input → read-back and delete-final (one shared create fixture) → paging. Then triage rules (D7, D8), ceilings and the report (D6, D12–D14) with the one golden regeneration. | If C overruns, what's left is exactly what the cut order says to keep. |

## Unchanged from the stage document

- Up to 5 resources per family; a 5 req/s request budget by default.
- `SPEC_MISMATCH` becomes an issue, never a PR, unless Clarify settles which side is intended.
- The report states which strategies ran and how many operations were excluded, and why.
- Done item: the template run is unchanged.

## Consequences for other stages

- **E:** safe mode is a guard in `platform_rt`'s session (D2), not a proxy. No separate `EXTERNAL_ENV` class (D8).
- **D:** produces the `needs_dependency` marker and which operations are secured, for a spec without security (D5, D9).
- **F:** priority scores replace D11's fixed order.
