# Skeleton — status (003, 2026-10-31)

Closes two gaps found while checking the skeleton against the product's user journeys
(the alignment review after [002](002-2026-10-31-status.md)). This entry adds to 002; it doesn't replace it.

## 1. Stage-specific UI panels (plan 2.2)

- `web/src/panels/registry.ts` collects panels at build time from `web/src/panels/*/index.tsx`
  (`import.meta.glob`, eager). A stage's folder **exports** `artifactPanels` (keyed by artifact
  type) and/or `reviewPanels` (keyed by review kind) using the types in `panels/types.ts`. It never
  edits skeleton files. Two panels for the same key fail the build.
- Artifact viewer: a registered panel replaces the generic body view, and the raw JSON stays
  collapsed below it. Review queue: a registered panel replaces the generic decision UI.
- `docs/folders.yaml`: `web/src/panels/<stage>` is owned by that stage and created at that stage's
  milestone. The registry and types stay with the skeleton.
- **Evidence:** a temporary `panels/zz_probe/` registering `cases` + `signoff` panels was picked
  up in the production bundle, then removed, after which the bundle had no trace of it. `tsc -b` passes.
  No stage panel exists yet; the folder rule forbids one before M1/M2.

## 2. Structured review decisions

- A review payload may carry `lines: [{id, text, …}]` (kinds in `LINE_OPTIONS`; currently
  `signoff` → approve/reject) or, for `question`, `choices: [{id, text}]` + `recommended`.
  Both are checked when the item is created.
- `resolve(item, decision, by, reason, detail)`:
  - Line items need `detail.lines` with a decision for **every** line. A reject needs a comment.
    The item's decision is derived (approve only if every line is approved), and a contradicting
    explicit decision is refused. A blanket `approve` without lines is refused.
  - A question's `pick` needs `detail.choice` to be one of the item's choice ids.
  - `defer` stays a whole-item decision with no detail (unattended mode uses it).
  - `detail` is stored on the item, in `decisions`, and in `decisions.jsonl`.
- The stub sign-off now has three lines. Rejecting a line re-opens **only that line** in a new
  item, carrying the reviewer's comment. The approved lines are not asked again (C5 behaviour,
  shown on the stub).
- API: `Resolve.decision` is optional and `Resolve.detail` was added; `ReviewItem` gained `detail` and
  `line_options`. CLI: `tp review resolve <id> [decision] --line ID=approve|ID=reject:comment
  --all-lines … --choice …`.
- UI: a generic line-by-line form (radio + comment per line; submit is enabled only once
  every line is decided and every rejection has a comment; there is no "approve all") and a
  generic choice form with the recommended choice preselected.
- **Evidence:** `39 passed`. New tests: `test_review.py` (reopen only rejected line, line
  validation, question choices) and `test_cli.py` (line flags, panel-folder ownership). Over HTTP via the
  Vite proxy: blanket approve → 409 "missing TC-1..3"; reject TC-2 → item 2 with only TC-2 and
  its comment; approve it → run `succeeded`.

## Breaking change

`review_items` and `decisions` gained a `detail` column. `CREATE TABLE IF NOT EXISTS` doesn't
add columns, so an existing `data/platform.db` from before this entry must be deleted
(`data/` is git-ignored dev state). There is no migration framework yet.
