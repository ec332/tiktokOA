# Discover & bootstrap — design (stage D)

Design debate of 2026-11-07. Inputs: `docs/iteration2/D-discover.md`, the master plan, `docs/status/checks/001-2026-11-07-design.md` (C's hand-offs: `data.id_field`/`id_style`/`paging`, `checks.families.exclude`, the `needs_dependency` marker, secured operations when the spec declares no security, Paperless masking secrets on read, Paperless documenting neither 404 nor 400), both fixture profiles (`tests/fixtures/targets/{paperless-ngx,memos}/profile.yaml`), `targets/fastapi-template/profile.yaml`, and the source D changes (`tp/core/profile.py`, `tp/core/llm.py`). The user accepted every recommendation below. `D-discover.md` and the master were updated to match this file. The master tracker's Status column was left alone at the user's request (stage C is building in another session).

## Decisions

| # | Topic | What the stage document said | Agreed | Why |
|---|---|---|---|---|
| D1 | Exploration loop shape (open question 1) | Open: one tool-using agent, or one prompt per step | **One structured prompt per step.** Fixed code gathers the context (file list, capped reads, earlier probe results with volatile values such as dates, generated IDs and tokens normalised), one Haiku call returns a ranked JSON candidate list, fixed code probes each candidate. If all fail, one more round with the failures fed back; after that, a `setup` question. | The gateway is a single prompt → text call, cached by prompt (`llm.py`); it has no multi-turn tool use. Bounded cost, and each step is testable with a scripted fake. |
| D2 | What "replays exactly" means | "Discovery replays from `llm_cache/` exactly" | **A replay serves probes from the recorded probe log and model calls from `llm_cache/`, with no Docker, and produces a byte-identical profile.** | Makes the done item checkable, and gives Docker-free tests of the whole discover stage. |
| D3 | First-user creation before Sign-off (open question 2) | Open | **Allowed for container reach, never for external reach** (external: supplied secrets only, unchanged). The bootstrap is **declared in the profile** (e.g. `auth.value.bootstrap: {op, body}` with the password as `{secret: admin_password}`) and fixed code replays it at every provision. The password is generated once and kept in `tp/core/secrets.py`. | It is setup on a throwaway container the platform owns. Discovery's admin lives in discovery's container; each run starts a new one, so without a declared bootstrap the discovered profile can't run. |
| D4 | `--no-conventions` side by side (open question 3) | Open | **A compare toggle on the Targets page**, not a separate page: one table of two profile artifacts at the same commit, field / normal (source, layer) / no-conventions (source, layer) / same value, with a footer of probes, model calls, cost and wall time per run. | Cheap, and shows exactly what the done item claims. |
| D5 | Where discovery runs and where `setup` questions live | `tp target add`; `setup` questions "at Clarify" | **`discover` is a registered stage.** `tp target add` is a run holding only that stage. Its `awaiting_review` items are the `setup` questions. Its output is a profile artifact, also written to `data/targets/<slug>/profile.yaml` so the existing loader and `TP_TARGET=<path>` (blackbox D13) work unchanged. An answer is verified by a probe and recorded as `source: clarify`. The gateway budget is set to $0.50 for this execution (the default is $3.00). | Clarify is review items inside a run, but discovery runs before any run exists. Being a stage reuses events, the review UI, the gateway budget, replay and caching per commit. |
| D6 | Profile schema | The example shows `creds`, `deps`, `ceiling`, `overrides` at the top level | **No new concerns.** `creds` → `auth.value` (login plus `bootstrap`). `deps` → `checks.families.exclude` entries with `reason: needs_dependency`. `ceiling` stays computed (`checks/001` D12). `overrides` is the count of fields with `source: override`. | `CONCERNS` in `tp/core/profile.py` has none of them; C already has the exclusion and ceiling mechanisms. |
| D7 | Per-field source and evidence | `source`/`evidence`/`layer` per concern | **An optional `provenance: {<sub-key>: {source, layer, probe}}` map on `Field`.** The concern-level `source` is the weakest of its sub-keys. Evidence ids point into a sealed, redacted `discovery_probes` artifact. | Done item 3 says "every field": e.g. `data.id_field` is probed while a timeout is a default; `reach.port` comes from the repo while `health` is probed. |
| D8 | Endpoint verification | "Each operation answers something other than 404/405"; Endpoints before Auth | **Step order: reach → spec → auth → credentials → confirm endpoints → data.** Endpoints are confirmed *with* credentials, against a fingerprint of a garbage path's 404 (status + content type + JSON keys). Writes are probed with an empty body (a 400/422 confirms the route without writing). Per-operation confirmation only for `repo_file` or inferred specs; a served spec is recorded as `probed` and not checked operation by operation. | A real route with an unknown ID returns 404 (DRF, grpc-gateway); auth middleware returns 401 even for routes that don't exist. A served spec comes from the running code itself. |
| D9 | Secured operations when the spec declares no security (C's D5 hand-off) | Not covered | **The default comes from the majority:** if most operations refuse anonymous calls, the default is `secured`. Operations that answer anonymously become **one** `confirm_observed` item ("these N operations answer without credentials; is that intended?"), never a silent `public`. Until answered, C treats them as `SPEC_MISMATCH` (its D5). | Labelling an operation public because an anonymous call got a 2xx would describe a real auth hole as expected (master §7, "inferred specs describe bugs as expected"). |
| D10 | Round-trip exclusions (Paperless masks secrets on read) | Not covered | **A field is excluded from round-trip checks only when the spec marks it `writeOnly` or `format: password`, or the read value is a constant mask** (e.g. `*****`). Any other field that differs goes to `confirm_observed`, never excluded automatically. Paperless documenting neither 404 nor 400 needs **nothing from D**: C's `status_code_conformance` reports it. | Same risk as D9: an automatic exclusion would hide a real round-trip defect. |
| D11 | `needs_dependency` | "Operations failing only because of them are marked and excluded" | **Marked only when the operation returned a 5xx during discovery and the container log for that request names an env var the code reads but nothing supplies** (a fixed match on the log). Otherwise the operation stays in and C reports the 5xx. It is an **exclusion reason** in `checks.families.exclude`, not a triage class. Built with one fake-backed test; it may fire zero times on the two targets. | No guesswork attributed to the AI. Same move as C's D8 (no extra class when the behaviour is the same). |
| D12 | Conventions vs algorithms | `config/discovery.yaml` kinds include `id_style` and `paging_param` | **Conventions are lists of candidate values** (paths, parameter names, env-var patterns) and are switched off by `--no-conventions`. **Probe algorithms always run.** ID detection uses no name list: try each scalar field of the create response as the read operation's path parameter and keep the one whose GET succeeds (finds `id` integers and `name` resource names the same way). Paging is verified by creating two items, requesting a page of size 1, and following `next`/`nextPageToken`. Kinds kept: `spec_path`, `health_path`, `admin_env_pattern`, `signin_op_pattern`, `paging_param`. Dropped: `id_style`. | Keeps the convention list honest: it holds framework knowledge, not detection logic. |
| D13 | Which commit; build or pull | Build at the commit under test; a README image only if its tag matches; Memos built from `scripts/Dockerfile` | **Default to the repo's latest release tag** (`@ref` overrides). Pull the published image for that tag if a registry manifest exists; otherwise build. The build path is covered by one fake-backed test and an optional `--build` flag. **This changes `blackbox/001` D4**, which expected Memos to be the first real build. | A release-tag image matches that tag's spec by construction. It removes the slow Memos build and the "`:stable` lags" risk. |
| D14 | Paperless "zero overrides" | Field-by-field match with B's profile (`blackbox/002` D13) | **A field-by-field comparator with explicit equivalences:** user and secret names may differ; YAML and JSON specs count as the same (`?format=json`); `read_back_timeout_s` is a platform default from config (`source: resolver`), not a probe; secret-like variables (`*SECRET*`, `*KEY*`, `*PASSWORD*` via `admin_env_pattern`) holding placeholder values in the repo's env files get generated secrets (covers `PAPERLESS_SECRET_KEY`). | The reference profile contains choices that aren't discoverable as written. |
| D15 | Template reproduction | Reproduce `profile.yaml`; only planted-bug extras stay overrides | **Discovery must reproduce reach (compose, services, health), spec (served, base) and the auth env vars.** Everything else (patches, testinfo, `transaction` state with harness and `db_probe`, flows, factories, mailpit, `scripts/prestart.sh`) stays an override with a listed reason. Built last; first to cut. | Most of the template profile can't be discovered; it is calibration extras (R11). |
| D16 | Budget | 15 min and $0.50 per target | **The 15 min / $0.50 excludes image pull and build time**; the record states both. | A Memos image build alone can exceed 15 min. |
| D17 | Build order | Not stated | **The build order is the cut order:** (1) discover stage skeleton, probe log, replay without Docker, profile writer with provenance, Paperless via conventions plus the comparator; (2) Memos: auth found by probing, replayed bootstrap, ID and paging detection, secured map and `confirm_observed`; (3) `--no-conventions` run; (4) Targets page with the compare toggle; (5) `setup` questions and answer verification; (6) `needs_dependency`; (7) the narrowed template reproduction. | 1.0 day doesn't cover everything; if D overruns, what's left is the part that matters most. |

## Unchanged from the stage document

- Three layers (conventions → exploration → `setup` at Clarify), every candidate verified by a probe.
- Conventions in `config/discovery.yaml` with required framework provenance; entries justified by a target are rejected.
- At most 5 `setup` questions; the rest sampled or `NOT_RUN` with a reason.
- External targets: supplied secrets only.
- The failure log `data/discovery/failures.jsonl` and its four classes.
- Haiku 5.5 by default, measured; results cached per commit.

## Consequences for other stages

- **C:** consumes `auth.value` secured defaults and the `confirm_observed` list (D9), round-trip exclusions (D10), and `needs_dependency` exclusions through its existing `exclude` list (D11). No new triage class.
- **B:** `blackbox/001` D4 (Memos as the first real build) is superseded by D13; the build path is covered by a fake-backed test and `--build`.
- **F:** `confirm_observed` items from discovery (D9, D10) join F's Clarify stops.
