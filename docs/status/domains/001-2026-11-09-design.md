Brief: `docs/iteration3/P4-domain-pack.md`. Settled by `docs/iteration3/rules.md` (U5), with no user debate. Serves FB-b, CR2, CR4, G1, SR3 (DR-5, DR-6, DR-12). ## Out (R1)

- A `tp pack validate` command (the check runs inside `pack run` and in the tests).
- A compare view in the UI, JSON output from `tp compare`.
- Feeding the vendored spec to discovery when an implementation has none (Request R3).
- The Hurl suite (P5 is cut; `suites: []`).

## Requests (for I1)

- **R1 (`tp/stages/env/blackbox.py`, `TokenHeaderAuth.principal`):** accept any 2xx from the login route, as discovery's `try_login` does (`discovery.py:600`). Without it, discovery on the notify fixture (and any app whose sign-up returns a token with 201) fails at the stand-in restart.
- **R2 (the black-box consumers of `spec.value.base`):** when the base comes from `servers` and the spec's paths don't start with it (RealWorld: base `/api`, paths `/articles`), requests must go to `base + path`. One place is the runner's `TP_BASE_URL` (`blackbox.py:690`): the stack URL plus the base, with `TP_API_BASE` (`blackbox.py:671`) left as it is.
- **R3 (`tp/stages/discover/discovery.py`, `step_spec`):** an implementation with no spec of its own (express-bookshelf) could take the pack's vendored spec. Today a `spec` answer must be a served path or a file in the repo.
