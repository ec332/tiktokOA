## 4. How the build differs from the brief and the design

- **D12 (refined, names `domains/001`):** a root server URL (`/`) falls back to the common prefix instead of giving `""`. A spec with `servers: [{url: /}]` whose paths carry `/api` would otherwise lose its base. That was a regression risk for targets discovered today. A templated URL also falls back, as designed.
- **D5:** run A on the fixture starts at generate. Its spec and cases are hand-written, empty and labelled `pre-generated`. So the full pipeline from a brief (`tp pack run`'s first run) is unit-tested for its order only. It runs for real in I1.
- **D4:** the fixture profiles are hand-written, because discovery on the fixture fails at the stand-in restart (Request R1).
- Not checked: whether the fixture runs' retest and deliver succeeded. The test asserts execute and what follows from it; the later stages were not inspected.

## 5. Requests (for I1)

- **R1 (`tp/stages/env/blackbox.py`, `TokenHeaderAuth.principal`, line 1006):** accept any 2xx from the login route, as discovery's `try_login` does. Without it, discovery of the notify fixture (and of any app whose sign-up returns a token with 201) fails: `the stack didn't come up with stand-ins: login /api/users: 201`.
